# 开发前置文档标准

本项目采用受 OpenAI Harness Engineering 启发的 agent 友好文档方式：仓库内
文档是事实记录系统，短入口负责导航，深入背景放到结构化 `docs/` 目录中。

参考：

- OpenAI Harness Engineering: https://openai.com/zh-Hans-CN/index/harness-engineering/

## 目的

开发开始前，必须先创建或更新一份执行计划。计划要让后续接手的人或 agent
不依赖聊天记录、个人记忆或临时说明，也能理解这次改动。

计划必须回答：

- 要改什么？
- 为什么要改？
- 会影响哪些文件、模块、流程或用户体验？
- 哪些约束必须保持成立？
- 怎样验证结果是正确的？
- 实现过程中做了哪些关键决策？

## 必须流程

1. 先阅读 `AGENTS.md` 和 `docs/index.md`。
2. 从 `docs/exec-plans/_template.md` 复制模板，在
   `docs/exec-plans/active/` 下创建计划。
3. 编码前先填完计划的核心内容。
4. 范围、决策、风险或验证方式变化时，同步更新计划。
5. 工作完成后，补充最终验证记录，并把计划移到
   `docs/exec-plans/completed/`。

## 计划必须包含

- 摘要：用一个短段落说明本次工作。
- 目标：这次改动要交付的用户或系统结果。
- 非目标：明确哪些事情不在本次范围内。
- 背景：相关文件、现有行为、相关文档和待确认假设。
- 影响范围：可能变化的模块、页面、接口、数据模型或工作流。
- 约束：架构、产品、安全、可靠性、体验或兼容性要求。
- 验收标准：完成后必须能观察到的结果。
- 验证计划：要运行的测试、人工检查、截图、日志、指标或命令。
- 风险与回滚：可能出错的地方，以及如何恢复。
- 进展记录：按日期记录实现过程。
- 决策记录：重要取舍和选择理由。
- 完成记录：最终结果、验证证据和后续事项。

## 写作标准

- 入口文档要短，通过链接指向更深层背景。
- 多写可检查的条件，少写模糊意图。
- 面向“看不到原始对话的未来接手者”来写。
- 稳定知识放进仓库，不只留在聊天里。
- 明确标注假设，确认后用事实替换。
- 发现过期文档要及时更新、删除或归档。

## 适合 agent 的约束

好的约束描述结果和不变量，而不是事无巨细地规定步骤。

示例：

- 跨越信任边界的数据，使用前必须校验。
- UI 改动必须检查桌面和移动端宽度。
- 新行为必须有聚焦测试；如果无法测试，要在计划中说明原因。
- 除非计划中记录理由，否则改动应遵循现有架构和命名风格。

## 质量门槛

当另一个工程师或 agent 能做到以下事情时，计划才算可以进入实现：

- 看懂本次改动要达成什么结果。
- 找到相关源码和文档。
- 理解本次改动的边界。
- 按计划运行验证步骤。
- 根据验收标准判断工作是否完成。

如果上述任一项不清楚，先完善计划，再开始编码。
